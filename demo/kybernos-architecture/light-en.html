Kybernos — how it works

Your machine runs the work. Your server holds the account, the models and the quota. A cloud machine keeps going when your laptop sleeps. Everything else is a door — and every door says what it carries.

Eight flows

01 An automation fires on this machine
  1. The scheduler ticks — every 30 s it rereads tasks.json and matches a cron, a date or a webhook.
  2. A DSH session starts — prompt and tools; in the default “ask” mode it will ask before acting.
  3. The model is called — through the server route (counted per space) or your own key.
  4. The run is written — last 20 runs in tasks.json; the board reads the session journal, never guesses.
02 An automation on the cloud computer laptop closed
  1. The platform wakes the machine — next_wake_at (0.5–0.7 s measured after first boot).
  2. Its own tasks.json fires — the machine has its DSH and its volume, so nothing is written remotely.
  3. It calls the model — through the server route, with the machine's restricted token; no secret is stored in it.
  4. Or a webhook wakes it — secret in the URL, the event appended to an existing automation's prompt.
03 Kaby from Telegram one message, one hosted turn
  1. The message reaches the server's bot — no tunnel, no open port.
  2. hosted.dispatch — it becomes a turn for you, on Kaby's thread.
  3. It runs on your cloud computer — only if the owner's switch is open (0 by default).
  4. The answer comes back — and the last words are told to your local Kaby: one assistant, two bodies.
04 The phone remote your Mac in your pocket
  1. A QR opens a channel — 26-character channel id, one-time code, identity key; the code never leaves the phone.
  2. The relay carries — one connection per computer, end-to-end encrypted, the server keeps only a digest.
  3. The phone renders your DSH — not a copy, not a cloud; Mac off means “offline”, no queue.
05 Opening the cloud computer a ticket, a gate, a page
  1. A ticket is asked — single use, for whoever may open it.
  2. The gate opens — single-use ticket, signed session, reverse proxy (the password is for a dev machine).
  3. You are in its DSH — page, assets and /api answer like a local session; the chat and files are the machine's.
06 A voice call you talk, the session answers
  1. The call belongs to the session — phone or camera in the chat header.
  2. A LiveKit room — the Python worker joins it.
  3. What it hears becomes a real turn — same model, tools and permissions as the chat.
  4. The voice comes back — the TTS you chose; video stays off without a face key.
07 Adding a custom server an address, not an installer
  1. You paste an address — DSH reads /.well-known/kybernos-server.json: it answers, publishes a profile, fits.
  2. The profile is accepted or refused — the registry file is written, then checked, then restored on refusal.
  3. The switch cleans the old route — previous model route removed first, new catalogue imported.
  4. Nobody is signed out — each server keeps its own connection file.
08 What the server sees of you account, plan, quota — and the rest
  1. Pairing — a device code, a token. No licence, no key by default.
  2. The active space pays — the model route carries the space header.
  3. The quota comes back — used percent, read on focus, every 2 min, and after a refusal.
  4. The rest stays — no files, no memory, no lessons, no sessions leave your disk.
