# @local/kybernos-phone-model

The small model that runs **on the phone itself** (Qwen3 1.7B, served by the Kybernos app on `127.0.0.1`), as a provider of the engine, with two presets: **Discussion** (plain chat: no tools, no files, no web) and, only when the app says its model takes tools, **Light agent** (four real tools, every write behind the person's approval). The full agent stays on the server. Contract: `LOCAL-MODELS-PLUGIN-CONTRACT.md` in the mobile repository.

**Inert** unless the app puts `KB_LOCAL_LLM_URL` and `KB_LOCAL_LLM_KEY` in the engine's environment *and* the platform is Android or iOS. On a desktop, in a cloud computer or in a build without the model, nothing is registered and nothing runs. `KB_LOCAL_LLM_ANY_PLATFORM=1` lifts the platform test (for the app's boot test on a Mac); it never lifts the loopback or the key tests.

## What it does, and nothing else

| Half | What |
|---|---|
| host (`index.js`) | every 10 s asks `GET <url>/v1/models`, keeps `llm-pi-ai.providers.phone-local` right (`openai-completions`, `apiKeyEnv: KB_LOCAL_LLM_KEY`, window 4096 declared to the engine as 8192, see 4 below; answers 1024); registers the preset `discussion`, and the preset `light-agent` while the model's row says `"tools": true`; gives the engine the prompt variable `kb_phone_now` (today's date); answers `GET /phone-model/state` → `{ available, installed, model }` (`model.tools`) |
| presets (`phone-model.mjs`, `discussion-scope.js`, `light-agent-scope.js`) | Discussion: persona only (≈ 175 tokens pessimistic, about 130 real: the ONE sentence to give for a reminder, a note, a search, an e-mail or anything to open or run, in English only, and the language of the LAST message), compaction sized for the real 4096 window (headroom 512, declared window 4096 larger, see below), and a plugin that hides every tool from that chat. Light agent: see « The light agent » below |
| page (`client.js`) | selects the preset the host names for a blank chat that uses the phone model (`light-agent` once registered, else `discussion`), read fresh from `GET /phone-model/state` right before the choice, and looks ONCE more at a blank chat the engine hands back already recorded as Discussion (see 9b); re-reads the host every 8 s while the line is on screen; one quiet line above the composer (`conversation.input.dock`: the label and the mode of the chat, « can set reminders » or « chat only (why) », « Manage models » → `kybernos://models`, or « Loading the model on this phone… » while the app says `phase: 'loading'`); moves a chat a flow opened (`kb-flow-chat`) to a cloud model; asks the app `{kybernos:'local-llm',version:1,op:'state'}` and reads its answers |

**Simple mode (2026-11-20).** The person has no model picker there, so the page applies the product rule « the phone's model answers when no other model can »: a BLANK chat, in the Kybernos app asking for Kaby mode (`KabyMode/<n>` in the user agent), whose model nothing can answer with (the engine's default with no key) is moved to the phone's model once, after a 3 s wait for the model directory to load (`wantsPhoneModel`, `catalogLoaded` in `client.js`). Any other usable model (a signed-in phone, a key) keeps the choice with the engine; a chat that started is never touched; outside Simple nothing changes. Once on the phone's model the chat takes the preset as before. Seen on 0.2.2-rc.5 and 0.2.1-rc.2 at 390 px (`scripts/check-kaby-mode-engine.mjs --simple`, with and without `--cloud-key`). The chip that says who answers is drawn by `kybernos-mobile` from the picker's label and `window.__KB_PHONE_MODEL__.seen.phone`; `__KB_PHONE_MODEL__.auto` says, for a live check, what the rule saw (providers and model counts, never a key).

It stores nothing. The key is never written, logged or returned by a route (the provider names the variable; the engine reads it from its environment). It never downloads, installs or deletes a model: that is the app's job.

## The light agent

A second preset next to Discussion (`light-agent`, « Light agent »): the same model with **four real tools** and a prompt of about 230 tokens with its date. The full agent (about 3 100 tokens of prompt and 87 tools on the phone's engine) cannot fit a 4096-token window, so this is a preset of its own. The mobile session measured the idea on a Mac (Ollama, Qwen3 1.7B Q4_K_M, thinking off, temperature 0.3): five light tools and a ~130-word prompt gave the right tool with valid arguments 60 times in 60.

The prompt's shape follows the ~130-token one the mobile session's Mac harness got 100 % from (Ollama, Qwen3 1.7B, temperature 0.3, 20 asks x 3 runs): a positive « use a tool when asked to… », one sentence for what no tool can do, « never say an action is done unless a tool result says so ». It is 20 tokens shorter than the previous text, and the model-facing tool texts are unchanged. Not in it, on purpose: « say "you" to the person » (on the stand-in it halved the calls with a time and did not remove « the user »), one example per tool (about 25 tokens each in a 4096 window). **What the text cannot fix** and is left to the app: the sampling (the Mac harness ran at 0.3, the phone's is unset), the model writing a call as text (`<tool>{…}</tool>`, `(memory_suggest "text": …)`: a fallback parser in native), the model answering in English to a French ask when it does not call. `node scripts/check-light-persona.mjs` replays nine asks against `llama-server --jinja` (a stand-in model) or `--ollama qwen3:1.7b` (the phone's own model, once pulled; 1.4 GB, the owner's word) at a given temperature; the stand-in has one dial (how readily it calls), so read it as a direction: **the phone is the bench**, and the cases to watch are the reminder with a time (must stay a call, in both languages), the one without (must ask), the question (must be answered) and a rejected card (must say nothing was set).

**The tools** (`LIGHT_TOOLS` in `phone-model.mjs`; each is a tool of this repository, a test compares every name, argument and type with the real definition, so a tool that disappears or an argument that is renamed fails the build):

| Tool | Job | Waits for the person |
|---|---|---|
| `automation_remind` | a one-time reminder (`message`, and `at` or `in_minutes`) | yes: the engine's own approval card, « Set this reminder? » with the words and the time. In the « Full access » mode (approval policy `never`) the engine shows no card and rejects every ask unseen: the reminder is then refused with a sentence that says it was NOT stored, so the model does not tell the person they refused |
| `automation_suggest` | propose a repeating automation (`name`, `prompt`, `cron`) | yes: it is stored switched off and waits for the person's « Add » |
| `memory_suggest` | propose a short note about the person (`text`) | yes: it waits for « Add » in Memory |
| `kaby_knowledge` | look in the person's own documents (nothing = list, `query`, `file`) | reads only; the result is cut to 2 400 characters |

Left out on purpose: `read` and the shell (the model would need a path on the phone, and a file can fill the whole window); `schedule_list` (it lists the engine's native scheduled tasks and `automation_remind` does not create one, it stores an automation: it would answer « none »); and **there is no tool that lists the person's automations** (the Automations page does that), so the prompt does not pretend.

**Small schemas.** The model sees a rewritten schema for each tool (a short description, few arguments: 1 560 characters of JSON instead of 4 290); the real tool still runs and still validates its own arguments, and every argument left out is optional in it. **No other tool reaches the model**: the global tools of the other bundles and the engine's nine team tools are not described to it, and a call to one anyway (a made-up call) is refused with one sentence naming the four, without running.

**The prompt** (`LIGHT_TEXT`, about 115 words plus the date line): who it is; use a tool only for those four jobs; if the request needs anything else, say plainly that it cannot and suggest a cloud model or Kaby; ask for a missing detail before acting and never guess a date, a time or a name (« set an alarm » became 08:00 in the mobile session's trial); say something is done only after a tool result says so, and that a proposal is waiting for approval; answer in the language of the LAST message. **Today's date** is a prompt variable (`kb_phone_now`) the engine fills in at every request: the weekday, the date, the time rounded down to 15 minutes (so the start of the prompt, and the cache that depends on it, changes at most every quarter of an hour), the time zone with its UTC offset, and the next seven days with their dates (a 1.7B model turns « vendredi » into a date badly; with the week written out it only has to look it up).

**The size, measured.** The whole first request the engine sent on 0.2.1-rc.2 (system prompt, the four schemas, a 45-character first message and the engine's runtime-context message) is about **760 tokens**: the four tools about 435, the prompt about 200, the rest the first message and the runtime-context message (about 90). Counted with the Qwen tokenizer on the Qwen3 chat template (`llama-tokenize` on the tev1 model's vocabulary, which is a Qwen3.5 one), then scaled by 0.80 so that the mobile session's own five-tool trial, which that count puts at 631 tokens, matches the 507 it measured on qwen3:1.7b: an estimate good to about ±10 %, not a count on the phone's model. The test holds the pessimistic count (one token per three characters) of prompt and schemas to 800. The compaction counts the 800 tokens as fixed part of the window on top of the Discussion's, so a chat with tool results condenses before it can overflow 4096 real tokens whether or not the engine counts the schemas in its pressure. The declared window is the same as Discussion's (real + 4096, see 4 below): the engine still asks for the whole 1024-token answer.

**The engine's team message cannot be left out from here, and it costs.** The engine adds two `required` runtime facts to every chat as one extra USER message that comes AFTER the person's own, whatever `includeRuntimeContext` says: the working directory, and the team plugin's « You are the Team Lead named "lead". Use list_agents({}) … send_message({ target: "<teammate name>", message: "..." }) » (387 characters, about 90 tokens, instructions for tools the chat does not have). The second phone test showed what it does to a 1.7B model: asked to set a reminder it wrote `send_message({ target: "teammate1", message: "I will remind you…" })` as plain text, an invented call and a false promise; on the local test model the message also made ordinary questions refused (11 of 40, against none without it) and sometimes got answered itself (« lead »). Tried and NOT working, on 0.2.1-rc.2 and on 0.2.2-rc.1 (the live check, `--upgrade` and Discussion runs: the message was still in the request): taking a required fact out of the prompt assembly (the engine puts it back when it admits the request), and registering a context of the same name from the chat's scope with no text (the team plugin registers its entry in the AGENT's own scope, which sits below the chat's and wins the name; the registration is accepted and does nothing). What would work is a filter where the request is read: the app's server dropping a user message that starts with « Current runtime context. » before it builds the prompt (about 90 tokens back in a 4096-token window, and the bait gone). That is the app's code, so it is asked of the mobile session, not done here. A second way, tried and working, is a config line of the mobile repository, not code: leave `@deepseek-ai/dsh-experimental-agent-team-profile` out of `payload/profile-ios/bundles.json` (the phone profile's bundle list). The team plugin is then never installed, the message is gone on 0.2.1-rc.2 (a scratch copy of the payload tool, the mobile repository untouched: Discussion 22 checks and light agent 34 checks green, the live check prints « not in the request »), and what is left of the engine's message is the working directory line (196 characters). The price is Agent Teams on the phone for every chat, cloud ones included (nine tools and a prompt section); the mobile session decides.
**What it does to the light agent, measured.** Through `llama-server --jinja` (llama.cpp's own chat template, the local model `tev1:0.8b`, a weaker stand-in for Qwen3 1.7B, thinking off, 24 requests per line, the request the engine really sent) the model called `automation_remind` for « remind me… » 3 times in 24 with the team message in the request and 13 to 19 times in 24 without it (10 in 24 with only the working directory line left); the rest it answered in prose. Fewer tools (reminder and note only) did not change the rate, a terser imperative persona changed it by a few points at most, and a sentence telling the model to ignore the message did nothing. Fewer tools do cost less: the four schemas are 654 of the 1 056 tokens of that request, `automation_suggest` and `kaby_knowledge` 236 of them (about 190 real tokens, around 6 s of prefill on the phone). Dropping them is a product choice, not made here. The real Qwen3 1.7B is not measured (no copy of its file here). The `max_tokens` the engine asks for stays at the full 1024 (checked on every request of the run).

**Four seams, none a patch.** `tools.restrict({ allow })` with the names the engine holds; the model-facing list through `tools.setExecutor` (0.2.2 and later) or the `system-prompt/assemble` listener (0.2.1-rc.2); `tools.guard` and a `tools/pre-execute` listener (the approval card, the refusal); a `tools/post-execute` listener (the cut). The date is `systemPrompt.variable`, registered by the host half only on a phone.

**How a person gets it.** The app marks the row of its model in `GET /v1/models` with `"tools": true` once its loopback server passes `tools` to the model and answers with OpenAI `tool_calls`. The host half then registers the preset (and takes it away if the flag goes) and says which preset to select in `GET /phone-model/state` (`preset`: `light-agent` once it is registered, `discussion` for a model without tools, `null` while the model takes tools but the preset is not registered yet, or before the first poll of the app has finished). The page reads that state FRESH right before it selects (first phone test, 2026-11-09: it had read the flag once at page load, before the host's first poll, and every chat after got Discussion), waits up to three seconds while the host says `null`, takes Discussion after that, and takes Discussion at once if the engine refuses the light agent for any reason but « the chat has started ». It shows the decision: « … · can set reminders » or « … · chat only (the app does not report tools for this model) » / « (the light agent was not ready) », and `window.__KB_PHONE_MODEL__` carries `tools`, `preset` and `decided` for a live check. A row without the flag (an older app, a model that takes no tools) keeps the page on Discussion: the app's server answers 400 `tools_not_supported` to a request that carries tools, and nothing here sends one. A chat that opens on Discussion stays there. « Create » (Automations, skills, teams) still leaves the phone model (see 9 below): those chats expect the full agent.

**Card « Une étape avant de discuter » / « One step before we chat » (step 6 part 3, 2026-11-23).** Simple only, and only when the app can manage the phone's models (`supported`), the small model is not on the phone (`phase` `none` or `failed`, never while it downloads or loads) and no other model can answer (`others === false`: the model directory has loaded and holds no model, nobody signed in, no key). The page then draws one card (`data-kb="phone-model-step"`, button `get-model`) that opens the app's models screen (`kybernos://models`), instead of a chat that has nobody to answer. Never outside Simple, never on a phone that has a model or another way to answer. Pure rule `needsModelStep`; tests in `test-client.mjs`.

## Where the contract changed

1. **The page picks the preset.** The engine has no binding model → preset, and a preset can only be chosen while the chat is blank. So the page selects `discussion` when the chat's model is `phone-local`; a chat already started on another preset gets a one-line note (« start a new chat »).
2. **No tools needs three steps, not a preset row.** The Kybernos tools are registered globally and the engine's nine team tools in every chat's own scope, so a preset without tool rows still sent 9 to 100+ tools. `discussion-scope.js` (mounted by the preset in each Discussion chat only) masks the global ones, tells the model about none, and guards every call. The « tells the model about none » step has two seams, picked by what the engine's registry offers: `tools.setExecutor` (0.2.2 and later: an executor that describes nothing) or, on **0.2.1-rc.2, the engine the phone ships**, a `system-prompt/assemble` listener that empties the `tools` of the assembly the request is built from. Both are proven on their own engine; `restrict` and `guard` exist on both.
3. **Compaction headroom 512.** The engine's default 65 536 refuses a 4096-token window.
4. **The engine is told a window 4096 larger than the real one.** The engine's request builder (pi-ai) asks the model for at most `window − prompt − 4096` tokens, and never fewer than one: with the real 4096 window every chat request carried `max_tokens: 1` and the answer stopped after one word (« Output token limit reached »), on 0.2.1-rc.2 and on 0.2.2 alike. The provider block therefore declares `contextWindow = real + 4096` (`ENGINE_ANSWER_MARGIN`), so the request asks for the full 1024 tokens, and the compaction adds the same 4096 to its headroom and sizes its kept tail on the real window, so a chat still condenses at the real size (2560 tokens of messages on a 4096 window). A side effect: a context gauge, if the engine draws one, reads against the larger window. `check-phone-model-chat` reads the exact `max_tokens` of every request and fails under 256.
5. **Provider removal.** An empty model list removes it at once; a dead server removes it after two polls in a row.
6. **The line lives on `conversation.input.dock`** (the slot the engine draws for a new chat too); `conversation.composer.dock` only appears after the first message.
7. **Picker label:** the provider's name is « On this phone » (a provider has one fixed name, no translation).
8. **The persona gives ONE sentence to say, in English, and the language last.** A 1.7B model told « You can only chat. You cannot create, save, schedule, search, open, read or run anything… If you are asked to, say so » read that back as its answer (« I am Kybernos, a small assistant running on this phone. I cannot create, save… », seen on the phone) or promised « I will remind you… » and created nothing. A list of things not to do is parroted; a sentence to say is used. The text is positive and short: who it is, answer briefly, the reply to give for a reminder, a note, a search, an e-mail or anything to open or run (« I can't do that here. Use a cloud model or Kaby on your computer. », said in the person's language), answer everything else normally. The French form that stood beside it is gone: the second phone test answered an English request with « I can't do that here. Utilise un modèle cloud ou Kaby sur ton ordinateur. », the two sentences spliced. The language rule is still the LAST sentence and names the person's LAST message (« in the language the person writes in » left a chat begun in French answering a later English question in French). Measured on the local Qwen model `tev1:0.8b` (smaller than the phone's 1.7B, so a harder test; thinking off, temperature 0.7, `node scripts/check-phone-persona.mjs`: 8 requests per case, 5 action requests and 5 ordinary ones, English and French, the request as the engine sends it, with the team message when it is still there): without the team message (`--no-context`: what the request would be if the app dropped it) the English-only text answered 30 of 40 action requests as told and 40 of 40 ordinary questions, with 2 answers in mixed languages; the two-language text mixed or swapped the languages in 21 of 40. With the team message in the request, as the engine sends it today, every text did worse (the same text: 20 of 40 as told, 11 ordinary questions refused), and a sentence telling the model to ignore a message that starts with « Current runtime context » did not help on this small model. The failures that remain on this small stand-in are French requests answered with a made-up « I can do that » (it cannot translate the sentence); the 1.7B is stronger, and the real one is the test on the phone. `qwen3:1.7b` itself is not installed here (a 1.4 GB download that nobody asked for).
9. **A chat a flow opens does not stay on the phone's model.** « Create » (Automations, Skills, Agent Teams, templates, feedback) opens a new chat with a prefilled `Skill … — …` text that is plain words to a model without the skill, and the new chat inherits the model last chosen. The core bundle's `kbAwaitNewSession` (the one helper those flows share) fires `kb-flow-chat` (`detail.sessionId`, `detail.startedAt`) when the chat exists, except for the plain chat (`kbStartPlainChat`, the Crew tab's « new chat » button: not a flow, fixed 2026-11-09 after a plain New chat was moved to Claude Haiku); the page ignores an event that arrives more than 8 s after the flow began (a page put to sleep in the middle of the wait fires it for whatever chat is current) and never moves a chat that has already started; the page then, if that chat's model is the phone's and within 15 s, selects the host's default model (else the first model of another provider) through the chat's own model directory and says so in the line (« This needs a cloud model: switched to … »); with no other model it keeps the chat and says « This needs a cloud model: the small model on this phone cannot do it ». A chat the person opens and picks the phone's model for is never touched.
9b. **A blank chat the engine hands back on Discussion is looked at again.** The engine keeps the blank chat of a workspace and reopens it under the preset its log recorded (`restoreBlank`, `createInWorkspace` of `dsh-client-ui-workspace`). After an earlier test (or an earlier version of this page, or a moment when the host had not finished its first poll of the app) that recorded preset is Discussion: the page saw a preset on the chat, drew the line and never chose the light agent (the second phone test: native said `tools=true` from its first read and the chat still ran on Discussion). A BLANK chat on Discussion is looked at again with the host's fresh answer (up to 30 s, the chat being on a safe preset meanwhile; again each time the host's answer changes and each time the model is chosen again, four asks to the engine at most per chat: the third phone test, 2026-11-20, showed the look made once per chat id gave up for good when the host was late) and goes to the light agent when the host names it; a chat that has started, or a host that names Discussion, is left alone, and a refusal leaves the chat where it was. The line's words (« can set reminders » / « chat only (why) ») come from the host's last answer, re-read every 8 s while the line is on screen: the first version of the line read it once at page load, before the host's first poll, and said « the app does not report tools » on a phone whose app does. Checked on the phone's engine with `node scripts/check-phone-model-chat.mjs --payload <dir> --upgrade` (a blank chat recorded on Discussion, the app then says its model takes tools, the page is reloaded).
9c. **The mode note says nothing until the page knows.** « chat only (the light agent was not ready) » came from `store.tools === true` and a chat recorded on Discussion, so it was drawn on the launch page while the page was still waiting for the host, and never recomputed. `modeNote` (pure, in `client.js`) now answers from the chat's recorded preset, whether it started, what the host names now and what the look above concluded: while the page is still deciding (host unknown, look pending, the engine's choice not recorded yet) the line shows its label and no mode; « not ready » (or « the app does not report tools ») only once the wait has ended or the host itself names Discussion; a chat that started, or one the engine refused as started, says « chat only (a new chat can set reminders) » when the host names the light agent and nothing when it does not know. `window.__KB_PHONE_MODEL__.seen` carries `host`, `recheck` (`pending` / `ended` / `locked`) and `mode` for a live check.
10. **`phase: 'loading'`** is a new value of the app's state (contract § 6): the model is installed and being loaded into memory. The line says « Loading the model on this phone… » then. A page that does not know the value reads it as `none` (as for every unknown phase), so the app can send it before every page is updated.
11. **The memory capture skips these chats** (`kybernos-cloud`, `NO_CAPTURE_PROVIDERS`). After every turn of a signed-in account the cloud bundle reads the turn back (`purpose: memory-capture`, `max_tokens: 300`, about 260 prompt tokens, an answer of `{"memories":[]}`) on the CHAT'S route to write lasting facts to the account's memory: on the phone model that was one more request after each answer, ahead of the next question, and what the person said would have been written to the account. `phone-local` chats are not read back.

12. **`"tools": true` on a model row** of `GET /v1/models` is a new optional field of the contract (§ 2): the model takes `tools` in the request and may answer with OpenAI `tool_calls`. Without it the bundle behaves as before (Discussion only).
13. **The device's time zone is read from the engine's own process** (`Intl`), which the light agent puts in its prompt and which `automation_remind` also uses when it is given no zone. The mobile host does not set `TZ` for the engine today; if the engine on a phone reports UTC, the person's « 9h » is an hour or two off. Not verified on a phone.

## Tests

```bash
node packages/kybernos-phone-model/test-host.mjs     # fake app server, keeper, route, preset, scope plugin (both engines' registries)
node packages/kybernos-phone-model/test-client.mjs   # the real page component on a small hooks runtime
node packages/kybernos-mobile/test-kaby-mode.mjs     # the `kb-app-message` seam on the shell side
bash -c 'source scripts/sandbox/env.sh; node scripts/check-phone-model-chat.mjs'            # real engine 0.2.2 in the sandbox, needs a GUI
node scripts/check-phone-model-chat.mjs --payload <payload dir>                              # real engine 0.2.1-rc.2, the phone's, from the app's payload
node scripts/check-phone-model-chat.mjs --payload <payload dir> --light [--dump <file>]      # the same, the app saying its model takes tools: Light agent
```

`check-phone-model-chat.mjs` starts the engine with a fake app server (random port and key), then proves: the provider reaches the engine and the picker, the first chat request has no `tools`, only system/user/assistant roles, a `max_tokens` of 256 to 1024 (every request of the run, the longer conversation too), ≤ 400 tokens, the app's `model_stopped` error shows its own sentence (mid-answer: a last `data:` frame with `{error}` and no `[DONE]`; before the first word: a plain 503), and the key is in none of the files the engine wrote. With `--payload` the engine is the one the phone ships: boot it from a payload built by `payload/build-payload.mjs` of the mobile repository (the bundle among its bundles); the first unpack takes a couple of minutes. It stops the engine and removes its throw-away folder at the end. It is not named `-live`, so the `check-all-live` battery does not run it (it restarts the engine with its own variables).

## What leaves the phone, measured

`check-phone-model-chat.mjs --payload` starts the phone's engine with a **Claude key that is a canary** (so the phone's first-run seed makes Claude the default model, as a signed-in phone has a cloud default) and `scripts/lib-egress-spy.mjs`, which refuses every connection off the machine and writes what it was and what it carried. After a French first message holding a word that exists nowhere else it asserts: that word is in nothing the engine tried to send away; the only calls to a model API after the message are the health probe of the connected providers (a one-token « ping »); the engine's own title call goes to the chat's route, the phone's server. Measured on 0.2.1-rc.2: the title (`session-title-llm`) has no model of its own in the profile, it uses the route of the chat's request, so on a phone chat it is the phone's model (a request of about 3900 answer tokens, the base profile's ceiling); the other attempts are the model list (models.dev), the server's catalogues, the version check and the npm registry: none carries the chat.

## What the light agent writes, and where

`automation_remind` stores a one-time automation in this device's automations and `automation_suggest` / `memory_suggest` put a proposal in the ledger that waits for the person's « Add »: this bundle adds no outbound call and sends nothing off the phone. Where those stores sync to is the business of their own bundles (kybernos-plugin automations, kybernos-memory), not changed here. `check-phone-model-chat.mjs --payload --light` runs the same egress spy as for Discussion through the whole tool round trip.

## Not verified

A real phone and the app's real server (the check's fake server answers `tool_calls` the way the OpenAI format says; the app's server does not take `tools` yet); that the real 1.7B model picks the right tool, writes valid arguments and reads the date right through THIS prompt and THESE schemas (the mobile session's 60 of 60 was measured on five other tools and a prompt of its own: the live test on the phone is the first real one); the prefill time of about 760 tokens on the phone (about 15 s at the 50 tokens a second the mobile session measured, minus whatever the model's cache keeps from one message to the next); the device's time zone on the phone (see 13); which permission mode a chat on the phone starts in (the card shows in the modes that ask and was seen on 0.2.1-rc.2; in « Full access » the reminder is refused with its plain sentence, seen on 0.2.2); the real Qwen tokenizer (the 400-token check uses a pessimistic one token per three characters); that the real 1.7B model obeys the persona (language of the last message, no claim of an action it cannot do) with the team message in its request (the real 1.7B may do better than the local stand-in, or invent `send_message(…)` again: the filter in the app's server is the sure fix): only the text and what the engine sends are proven here; a signed-in Kybernos Cloud account on the phone (the spy runs with a Claude key, not the account), so a cloud-side title or sync is not covered.
