# Copy the file-first pattern, not Univer

Kybernos should not build its Office layer on Univer, and it cannot "migrate to the Manus stack", because that stack is three different engines, two of them paid. It should copy what Claude, ChatGPT/Codex and Manus all do underneath: the agent edits real .xlsx, .docx, .pptx and PDF files through scripts or a command-line tool, recalculates and renders them with LibreOffice, looks at the result, and the person gets a viewer with a comment loop rather than a full editor. First-hand evidence from the owner's own Manus account settles the open question: Manus's Word editor is **eigenpal/docx-editor** (Apache-2.0 core, paid Pro packages), its spreadsheet is **SpreadJS** (commercial), its slides studio is **in-house HTML with server-side PPTX/PDF export**, and its agent side is **OfficeCLI plus LibreOffice plus HTML** (owner's Manus capture, 2026-11-02). Univer appears nowhere in it, and no source shows Claude or OpenAI embedding any third-party editor. Univer's core is Apache-2.0, but what an agent product needs most (the documented Slides stack, xlsx/docx/pptx import-export, charts, the AI toolkit) sits in `@univerjs-pro` packages with no published licence text, a free tier that is "evaluation" only (watermark, 10 exports a month) and a price model built around one hosted domain ([Univer pricing](https://univer.ai/pricing)); its vendor already ships an Apache-2.0 `dsh-univer-office` plugin into the same engine ([repo](https://github.com/dream-num/dsh-univer-office)). Kybernos today has no Office tooling of its own, leans on proprietary Anthropic skills whose Python and LibreOffice runtimes are missing on the reference Mac, does not list docx/xlsx/pptx files on its Creations page, and gets only a read-only preview from the engine (repo audit of `dev`). The plan is three stages: an Apache-2.0 file layer built on OfficeCLI and the LibreOffice kit DSH already carries; a human layer chosen per format (extend your own slides panel and add PPTX export, run time-boxed bake-offs for sheets and docs, no editor for PDF); and paid engines only as optional private modules. Four decisions are the owner's: whether people edit inside Kybernos at all, whether to pay for engines, whether to ask DreamNum for written terms, and what to do about the proprietary Anthropic skills. This is research, not legal advice; every licence reading below is flagged as a reading.

## The answer in plain words: edit real files first, add editors only where they pay

Two separate jobs hide inside the question. The first is making and changing the file: an agent has to produce a correct workbook, document, deck or PDF, with formulas that calculate and layouts that do not overflow. The second is letting a person look at it, comment on it or change it inside Kybernos. Claude, ChatGPT/Codex and Manus solve the first job the same way, with code or a command-line tool working on the real file, and they differ only on the second. Four levels help to name the second job: level 1 is viewing the file and opening it in the person's own app; level 2 is viewing it and commenting on a cell, paragraph or slide region so the comment goes back to the agent; level 3 is small edits in the panel that save back to the file; level 4 is a full Office-grade editor. OpenAI's desktop app sits at levels 1 and 2 (preview plus region annotations) ([OpenAI Learn](https://learn.chatgpt.com/docs/artifacts-viewer?surface=web)); Claude's chat sits at level 1 and reaches level 4 only inside Microsoft's own applications through add-ins ([Claude for Excel](https://claude.com/docs/office-agents/excel.md)); Manus reaches level 3 with three separate engines and a comment layer (owner's Manus capture). Univer is a level-4 product. Two names recur below: OfficeCLI is a small free program that lets an agent read and change Word, Excel and PowerPoint files, and the LibreOffice kit is a free office engine that DSH already carries, used here without a screen to recalculate, convert and draw pages. The recommendation is to build levels 1 and 2 for every format now, because they are cheap, licence-clean and proven by the leaders; to reach level 3 where Kybernos already owns code (slides) or where a short bake-off proves it (sheets, docs); and to keep level 4 out of the Apache-2.0 core. Effort below is my estimate: small means days, medium one to three weeks, large one to two months. Each cell is backed by the evidence sections that follow.

**Slides**

| Question | Answer |
|---|---|
| Use now | Keep `kybernos-slides` as the editor. Widen its model (images, tables, charts, columns, timeline), save decks to disk, export PPTX with PptxGenJS and PDF by printing the slides. For a deck the user brings, the agent edits the file (OfficeCLI or pptx-automizer) and the panel shows a LibreOffice render. |
| Why | It is the only place Kybernos already has a human-and-agent editing loop; no maintained permissive slide editor with PPTX round-trip exists; Manus does the same thing (in-house HTML studio, server-side export). |
| Licence | PptxGenJS MIT, pptx-automizer MIT, OfficeCLI Apache-2.0, LibreOffice MPL-2.0. Avoid PPTist (AGPL) and Univer Slides Pro. |
| Effort | Medium for export alone; large for the richer model plus persistence. |
| Does NOT give | Open any deck and edit it visually at PowerPoint fidelity, animations, SmartArt, identical text wrapping. Export from a structured model, not from free-form HTML, which Manus itself found lossy. |

**Spreadsheets**

| Question | Answer |
|---|---|
| Use now | Real .xlsx written by the agent with OfficeCLI (or an Apache-2.0 script of your own), recalculated and rendered with the DSH LibreOffice kit, shown in the existing preview, listed in Creations, with a cell-comment loop back to the agent. |
| Next, only if people must edit | A time-boxed bake-off: IronCalc engine versus Univer's Apache-2.0 Sheets UI, each with your own xlsx mapping. SpreadJS (Manus's choice) only as a paid private module. |
| Why | A spreadsheet editor is the hardest of the four (formula engine plus faithful xlsx), and even Manus uses a commercial component. The agent-side recipe (OfficeCLI, then LibreOffice recalculation) is first-hand proven at Manus. |
| Licence | OfficeCLI Apache-2.0, LibreOffice kit MPL-2.0, IronCalc MIT or Apache-2.0, Univer OSS Apache-2.0, SpreadJS commercial. |
| Effort | Small for the file layer; large for an editor. |
| Does NOT give | Editable charts and pivots on the free path, full Excel function parity, or a safe round-trip of workbooks with charts through IronCalc (the chart was lost in the one test run). |

**Documents**

| Question | Answer |
|---|---|
| Use now | Real .docx made by an Apache-2.0 script (docx.js or OfficeCLI), edited by patching the file, previewed as LibreOffice-to-PDF. Do not convert a customer's Word file into an HTML editor model. |
| Next, only if people must edit | A time-boxed spike of eigenpal/docx-editor's Apache-2.0 core (what Manus runs), with Tiptap core plus docx.js as the fallback. |
| Why | The shelf cards already promise a .docx, Word is the format where the original file matters, and eigenpal is the only permissive editor found that works on the real DOCX. |
| Licence | docx.js MIT, mammoth BSD-2-Clause, eigenpal core Apache-2.0 (Pro packages paid), Tiptap core MIT (Pro proprietary), BlockNote core MPL-2.0 (xl packages GPL-3.0). |
| Effort | Small to medium for the file layer; medium to large for an editor. |
| Does NOT give | Tracked changes and comments in the editor (Pro at eigenpal, paid and alpha at Tiptap), Word-exact pagination, or a lossless round-trip through HTML editors (floating images, text boxes and sections are dropped). |

**PDF**

| Question | Answer |
|---|---|
| Use now | No editor. Create from HTML (Electron or Chromium print, or LibreOffice), view with the browser viewer and the pdf.js already in the engine, merge, split and fill forms with scripts (pypdf, a maintained pdf-lib fork), OCR with Tesseract; add pdf.js annotation later. |
| Why | All three leaders treat PDF as an output and a render target; no permissive library edits existing body text. |
| Licence | MIT, BSD and Apache-2.0 only. MuPDF/PyMuPDF and Ghostscript (AGPL) stay out; Poppler and pandoc (GPL) only as user-installed separate programs. |
| Effort | Small. |
| Does NOT give | Editing text inside an existing PDF, true redaction without a custom script, or a Univer-style PDF editor (Univer lists PDF but it was not evaluated). |

## Claude, ChatGPT and Manus build files with code and check them by eye

**Claude** gives the model "a private computer environment where it can write code and run programs" ([Anthropic](https://claude.com/blog/create-files)). Four skills (xlsx, docx, pptx, pdf) tell it to create with openpyxl, docx-js, pptxgenjs and reportlab, and to edit by unzipping the file, editing the raw XML and zipping it again, then validating against vendored schemas ([xlsx skill](https://github.com/anthropics/skills/blob/main/skills/xlsx/SKILL.md), [docx skill](https://github.com/anthropics/skills/blob/main/skills/docx/SKILL.md)). LibreOffice headless is the one engine for formula recalculation, tracked-change acceptance and previews: the xlsx skill's `recalc.py` drives it through a Basic macro and then scans for error values ([recalc.py](https://raw.githubusercontent.com/anthropics/skills/main/skills/xlsx/scripts/recalc.py)), and visual checks go through PDF, `pdftoppm` and the model looking at the images. Claude has no editor in chat. Its separate Excel, Word and PowerPoint add-ins are Office task panes that call the host application's own object model, so the real application is the editor ([manifest](https://pivot.claude.ai/manifest-excel.xml), [Word add-in](https://claude.com/docs/office-agents/word.md)); Anthropic has not published their tool list. The skill files are "Proprietary": the licence text forbids extracting the materials from Anthropic's services, copying them, making derivative works or redistributing them ([LICENSE.txt](https://raw.githubusercontent.com/anthropics/skills/main/skills/docx/LICENSE.txt)), so only the workflow can be reused, not the scripts. The public repo also lags production by about three months ([open issue 2104](https://github.com/anthropics/skills/issues)).

**OpenAI** follows the same shape. ChatGPT's code container has a `/home/oai/skills` folder covering spreadsheets, docx and PDF, with a render-to-PNG loop ([Willison, 2025-12-12](https://simonwillison.net/2025/Dec/12/openai-skills/)). Third-party copies of that folder show a proprietary `artifact_tool` library for xlsx and pptx, python-docx for Word and reportlab for PDF ([spreadsheets skill copy](https://raw.githubusercontent.com/Last-emo-boy/oai-skills/main/spreadsheets/SKILL.md)); the copy's provenance is unverified. Codex goes further and ships a roughly **1.7 GB local runtime** with a headless LibreOffice build (430 MB), Node, Python and Poppler so it can edit and render Office files offline ([Willison, 2026-09-01](https://simonwillison.net/2026/Sep/1/codex-libreoffice/)). Its desktop app previews documents, presentations, spreadsheets and PDFs beside the chat and lets the user select a region to request a focused change, while the CLI has no preview at all ([OpenAI Learn](https://learn.chatgpt.com/docs/artifacts-viewer?surface=web)). No embedded third-party editor was found. OpenAI's public `openai/skills` repository is deprecated, though its `pdf` skill is Apache-2.0 ([repo](https://github.com/openai/skills)).

**Manus**, per first-hand evidence that overrides the web-research guesses, runs three different engines, each in its own sandboxed iframe on its own origin and talking to the shell through a postMessage bridge (owner's Manus capture). Word is the open-source **eigenpal/docx-editor**: its core is Apache-2.0, while tracked changes, comments, the Office.js subset and PDF export are Pro packages that need a commercial agreement ([repo](https://github.com/eigenpal/docx-editor)). Excel is **SpreadJS** by Mescius, a commercial canvas spreadsheet in an 11 MB bundle with a `LicenseKey` field. A PowerPoint file opened as a file uses an unnamed Rust-WASM parser with ProseMirror. The Slides studio is **home-made** (about 195 KB of JavaScript, no editor library): one HTML file per slide with Tailwind, versioned, with PPTX and PDF produced by an asynchronous server-side conversion. On the agent side, Manus's xlsx skill uses OfficeCLI and then a LibreOffice round trip to cache formula values, and its Word and PDF deliverables come from one HTML file converted by LibreOffice, with DOCX produced via ODT in two passes (owner's Manus terminal pastes). Manus's own blog adds a beta "PowerPoint mode" (July 2026) that writes a native .pptx because the older "web format converted on export" caused formatting problems (*vendor claim*) ([Manus blog](https://manus.im/blog/manus-ppt-slides)); the two slide paths coexist. Still unproven: whether Manus holds an eigenpal Pro licence, what SpreadJS costs it, and how Annotate comments reach the agent.

| Product | Agent creates files with | Person sees or edits with | Third-party editor embedded | Confidence |
|---|---|---|---|---|
| Claude (chat, API, desktop) | Sandbox skills: openpyxl, docx-js, pptxgenjs, reportlab, XML edit, LibreOffice | Download; preview | None found | High (skill files read) |
| Claude add-ins | Office.js against the open file | Excel, Word, PowerPoint themselves | The host application | Medium (tool list unpublished) |
| ChatGPT / Codex | Skills plus proprietary `artifact_tool`, python-docx, reportlab, LibreOffice render | Read-only preview plus region annotation | None found | Medium (official pages unreadable, copies unverified) |
| Manus | OfficeCLI, LibreOffice, HTML; Typst installed | Three separate engines in iframes plus Annotate, Quote, Comment | eigenpal docx-editor, SpreadJS | High for engines (first-hand), low for licences held |

Other agent products point the same way. Z.ai's slide agent emits HTML per slide and exports PDF or HTML ([BigModel docs](https://docs.bigmodel.cn/cn/guide/agents/glm-ppt.md)); MiniMax publishes MIT skills built on PptxGenJS and the OpenXML SDK ([repo](https://github.com/MiniMax-AI/skills)); Gamma built its own ProseMirror editor ([forum post, 2022](https://discuss.prosemirror.net/t/showcase-gamma-a-presentation-editor-built-in-prosemirror/4834)). Univer's site lists Genspark, Z.AI and Mistral AI as users (*vendor claim*, [univer.ai](https://univer.ai)), but searches found no corroboration, and a Chinese tech outlet says leading agent products are only running proof-of-concept tests with it ([36Kr](https://eu.36kr.com/en/p/3675553046831752)). Manus is not on that list, and its code shows no Univer.

Three lessons transfer. First, the shared weakness is that LibreOffice is both calculator and renderer, so anything it computes or lays out differently from Excel or PowerPoint is invisible to the agent; Codex users see Times New Roman silently replaced by Liberation Serif ([openai/codex #37179](https://github.com/openai/codex/issues/37179)). Second, new formulas arrive without cached values: Manus's own skill says OfficeCLI formulas ship uncached, which sits uneasily with OfficeCLI's README claim that 350+ functions are evaluated on write (*vendor claim*, [README](https://github.com/iOfficeAI/OfficeCLI)); either the builds differ or the claim is overstated, so test it rather than trust it. Third, LibreOffice's recalculation re-saves the whole package, which can alter styles, charts and validation (*inference*), so keep the authored file and the recalculated copy separate. Manus's per-format iframe isolation is the architecture worth copying, because it keeps a heavy library from breaking the host.

## Univer: an Apache-2.0 core with the agent-critical parts behind Pro

Univer's licence picture is two products sharing a name. The repository and the `@univerjs/*` packages on npm are Apache-2.0 (1.3.1); the `@univerjs-pro/*` packages carry no licence field, ship no LICENSE file and, per Univer's own CLI notes, "retain their own terms" ([registry](https://registry.npmjs.org/@univerjs-pro/slides), [univer-cli README](https://raw.githubusercontent.com/dream-num/univer-cli/main/README.md)). The README's own table decides what is free ([README](https://github.com/dream-num/univer)).

| Package family | Licence | Free gives | Needs Pro |
|---|---|---|---|
| `@univerjs/core`, `sheets`, `sheets-ui`, `docs`, `docs-ui`, `engine-*`, presets | Apache-2.0 | Sheets: editing, formulas, number formats, validation, conditional formats, comments. Docs: model, editor UI, lists, links, comments | Sheets and Docs: collaboration, history, import/export, print; Sheets: charts, pivots, sparklines, shapes; Docs: enhanced tables, code blocks |
| `@univerjs/slides`, `slides-ui` | Apache-2.0 | A basic deck: rich-text boxes, rectangles, images; no Facade, no preset, no import/export, no charts or tables | n/a |
| `@univerjs-pro/slides`, `slides-ui`, `license`, `exchange-*`, `engine-shape` | No licence field | A watermarked evaluation mode | The documented Slides product, conversion, licence checks |
| `univer-cli`, `dsh-univer-office` | Apache-2.0 repos | The agent harness code | Run on Pro bindings and a vendor credential |

The Slides "conflict" resolves into two parallel stacks. The open example mounts only `@univerjs/slides` and `slides-ui` and exercises text, shapes and images ([mount.ts](https://raw.githubusercontent.com/dream-num/univer/dev/examples/src/slides/mount.ts)); the documentation says "Univer Slides is provided in the `@univerjs-pro` package scope" and installs only Pro packages ([installation](https://docs.univer.ai/guides/slides/getting-started/installation.md)). The pricing page confirms the open edition has only "a basic Slides model" ([pricing](https://univer.ai/pricing)). Whether the open slides UI can actually insert and format anything is unknown; a 30-minute spike of the repo example would settle it.

The commercial terms do not fit a local-first app yet. The free tier is "Evaluation", watermarked, limited to three editing connections and **10 exports a month** (imports are unlimited), with printing capped. Business costs **$99 a month or from $1,000 a year**, covers one or two servers and "one main domain and all subdomains", and lets you distribute under your own brand but not resell the SDK ([pricing](https://univer.ai/pricing), a fetch-tool summary of a vendor page). That model suits a hosted service; many laptop installs with no fixed domain are not addressed anywhere public, and the commercial agreement text could not be found (`univer.ai/license` returns 404; only the mechanics are documented, in the [server licence page](https://docs.univer.ai/server/license)). A licence is two files checked offline with an Ed25519 signature, which a summariser's read of the minified code supports (*low confidence*, [license bundle](https://cdn.jsdelivr.net/npm/@univerjs-pro/license@1.3.1/lib/es/index.js)). My reading is that shipping Pro packages to end users in watermarked mode is outside the stated terms, and that a many-install deal needs a written OEM agreement.

Import and export is where the free path ends. Documented browser import and export of xlsx, docx and pptx needs the Server SDK's conversion service and a licence ([Sheets](https://docs.univer.ai/guides/sheets/features/import-export.md), [Slides](https://docs.univer.ai/guides/slides/features/import-export.md)), and version 1.2.0 removed the built-in menus. Univer's own Node tools convert locally through Pro native bindings, which is undocumented for third parties ([univer-cli README](https://raw.githubusercontent.com/dream-num/univer-cli/main/README.md)). The only free route is community xlsx converters, stale and Sheets-only ([`@zwight/luckyexcel`](https://registry.npmjs.org/@zwight/luckyexcel)); no free docx or pptx converter was found. Univer itself warns that complex formulas, charts, fonts and embedded objects may differ after conversion (*vendor claim*).

On agent fitness Univer is ahead of most rivals: a Facade API per product, JSON snapshots, headless Node for Sheets and Docs (the guides list no Slides equivalent), and an AI SDK with inspect, execute, screenshot and lint tools plus draft "worktrees" for human review ([AI SDK](https://docs.univer.ai/ai), [Sheets headless](https://docs.univer.ai/guides/sheets/getting-started/node.md)). But the layer is young. Univer reached 1.0 on 2026-09-23 and has shipped about weekly since, with breaking changes in most minors, all packages pinned to one version, and 0.25 on security-only updates for a year ([v1.0.0 notes](https://api.github.com/repos/dream-num/univer/releases/tags/v1.0.0), [releases](https://api.github.com/repos/dream-num/univer/releases?per_page=8)). Its MCP server was archived on 2026-10-28 after seven commits ([univer-mcp](https://github.com/dream-num/univer-mcp)), and the pricing page lists the AI SDK under the commercial tiers. The 68.86% SpreadsheetBench score is company-reported ([univer.ai](https://univer.ai)). The three largest engine packages weigh 25 to 41 MB unpacked each, the editors render to canvas, need React as a peer and have no documented accessibility ([registry](https://registry.npmjs.org/@univerjs/engine-render)).

The DreamNum plugin deserves its own paragraph because it targets the same engine. `dsh-univer-office` 0.4.0 (Apache-2.0, 657 stars, 27 releases in 11 weeks) gives a DSH agent 14 tools to create, inspect, execute, lint, screenshot and export Sheets, Docs and Slides with an approve-before-merge draft loop and a live viewer ([repo](https://github.com/dream-num/dsh-univer-office), [registry](https://registry.npmjs.org/dsh-univer-office)). Its constraints, from its own README ([README](https://raw.githubusercontent.com/dream-num/dsh-univer-office/main/README.md)): it is **162 MB unpacked** and needs a local Chrome, Chromium or Edge for screenshots, PDF and slide checks; while its bundled guidance is on it replaces DSH's own office skills; it runs a gateway on port 9080 and serves a viewer from the DSH web origin; authenticated browsers "can address any `.univer` file accessible to the Host process"; it sends anonymous telemetry unless disabled; slide masters, layouts and speaker notes are out of editing scope; and the licensing of the Pro bindings inside it is not stated. Its declared DSH range stops at `^0.2.1-rc.3`, while Kybernos runs `0.2.2-alpha.2`; the two have not been tested together. The plugin proves that a Pro runtime can ride inside an Apache-2.0 DSH plugin, but only the vendor itself is shown to be allowed to do so.

The verdict is that Univer is the right answer to "one SDK for four formats" and the wrong foundation for this product. Building on it would make Kybernos a reseller of a vendor's agent harness, with the vendor shipping a free competing plugin into the same engine and holding the pricing lever on the features that matter. Univer stays on the table in two narrow roles: its Apache-2.0 Sheets UI as a bake-off candidate, and `dsh-univer-office` as an optional neighbour users may install. The triggers to revisit are written OEM terms for local redistribution, a spike showing the open Slides UI is usable, and an acceptable price.

## The permissive parts exist; nothing replaces Univer end to end

For **spreadsheets**, the best permissive pair is **IronCalc** (MIT or Apache-2.0, Rust compiled to WebAssembly, version 0.9.1 released 2026-10-21) for the engine and xlsx input-output ([GitHub](https://github.com/ironcalc/IronCalc), [npm](https://registry.npmjs.org/@ironcalc/wasm-xlsx)). The researcher's own test ran it headless in Node 26 with formulas, XLOOKUP, undo and redo; a round trip of one workbook kept formulas, conditional formats, merges, frozen panes, widths and styles but **dropped a chart and a data-validation rule**, and charts are "not planned for version 1.0" ([unsupported features](https://docs.ironcalc.com/features/unsupported-features.html)). Its React UI package is immature. **Fortune-sheet** (MIT) is a complete grid UI, but its core has had no commits since 2025-11-06 ([repo](https://github.com/ruilisi/fortune-sheet)); the engine's Files sidebar already uses it read-only. Handsontable with HyperFormula is the most capable pair and is GPL-3.0 or commercial, with a clause against building "competitive" software ([Handsontable licence](https://raw.githubusercontent.com/handsontable/handsontable/master/LICENSE.txt), [HyperFormula licence](https://raw.githubusercontent.com/handsontable/hyperformula/master/LICENSE.txt)). SpreadJS, Manus's choice, is priced per developer (two snippets of the vendor page disagree: $999, or a $1,999 bundle) plus an annual hostname-based deployment licence, with one example at $12,499 for a single domain (*snippets of the vendor page*, [Mescius](https://developer.mescius.com/spread/pricing)), which sits badly with local installs. On the file side, SheetJS Community cannot write cell styles and its npm copy is frozen at 0.18.5 with two known advisories ([SheetJS docs](https://docs.sheetjs.com/docs/getting-started/installation/nodejs)); ExcelJS (MIT) is unmaintained since January 2024 and has no chart model ([repo](https://github.com/exceljs/exceljs)). OfficeCLI is Apache-2.0, a 34 MB single binary with path-addressed edits, a validator, a renderer and a pivot-table writer, but it is **7.5 months old with 6,148 of about 6,287 commits from one account** ([GitHub API](https://api.github.com/repos/iOfficeAI/OfficeCLI)).

For **documents**, the editor cores that fit an Apache-2.0 repo are ProseMirror, Tiptap core, Lexical (MIT) and BlockNote core (MPL-2.0); anything Word-like on top is paid or copyleft. Tiptap Pro is proprietary and must be deleted from your products when the subscription ends ([licence](https://tiptap.dev/docs/pro-license)); BlockNote's export packages are GPL-3.0 ([pricing](https://www.blocknotejs.org/pricing)); SuperDoc is AGPL or $6,000 a year ([site](https://www.superdoc.dev/)). ProseMirror's GitHub home was archived on 2026-04-01 and moved ([notice](https://github.com/ProseMirror/prosemirror)). **eigenpal/docx-editor** is the one permissive editor found that edits real DOCX natively, with a layout engine and WASM text shaping; it is young (npm package created 2026-07-16) and a third-party archive claims it "went dark" while its GitHub page was live, so its health is unresolved ([registry](https://registry.npmjs.org/@docx-editor.dev/core)). For writing files, **docx.js** (MIT, 9.15.1 on 2026-10-31) now covers comments, tracked-change runs, charts, HTML-to-docx and a placeholder patcher ([docs](https://github.com/dolanmiu/docx)); Tiptap's own support matrix shows what any HTML-editor pipeline loses: floating images, text boxes, shapes and sections ([matrix](https://tiptap.dev/docs/conversion/getting-started/feature-support-matrix.md)). Genspark's GenOffice (Apache-2.0 apart from an `ee/` folder) shows the pattern worth copying for real files: keep each block anchored to its original XML and splice only the changed blocks back ([README](https://raw.githubusercontent.com/genspark-ai/genoffice/main/README.md)).

For **slides**, no permissive, maintained editor with real PPTX round trip exists. PPTist is the mature one and is AGPL-3.0, with a separate Chinese-yuan commercial licence and no SDK or support ([README](https://raw.githubusercontent.com/pipipi-pikachu/PPTist/master/README.md)). The MIT tools write rather than edit: PptxGenJS creates decks (it does not read them) ([repo](https://github.com/gitbrent/PptxGenJS)), pptx-automizer fills real templates ([repo](https://github.com/singerla/pptx-automizer)), and dom-to-pptx turns DOM into absolutely positioned native shapes ([repo](https://github.com/atharva9167j/dom-to-pptx)). Slidev's editable-PPTX mode shows the ceiling of the DOM-to-PPTX idea: SVG, gradients, filters and KaTeX stay pictures and fonts are named, not embedded ([Slidev](https://sli.dev/guide/exporting)).

For **PDF**, generate with Chromium or Electron print (`printToPDF` returns a buffer, [Electron](https://www.electronjs.org/docs/latest/api/web-contents)), read and render with pdf.js (Apache-2.0, though a 2026 advisory covers arbitrary script execution from a malicious PDF, [advisory](https://github.com/advisories/GHSA-hq66-cqwq-w95j)), modify with the maintained `@cantoo/pdf-lib` fork ([repo](https://github.com/Cantoo-scribe/pdf-lib)) or pypdf, and OCR with Tesseract. MuPDF and PyMuPDF are AGPL ([PyMuPDF](https://github.com/pymupdf/PyMuPDF)).

Full suites are the heavyweight alternative. ONLYOFFICE Community is AGPL-3.0 with extra notice and branding terms rewritten on 2026-05-13 ([commit](https://github.com/ONLYOFFICE/DocumentServer/commit/a07795c4bd64f29552b9419ce1dd7bba822ca562), [FAQ](https://helpcenter.onlyoffice.com/docs/faq/docs-community.aspx)), a 943 MB Docker image ([Docker Hub](https://hub.docker.com/v2/repositories/onlyoffice/documentserver/tags?page_size=6&ordering=last_updated)) and a 4 GB RAM guideline ([system requirements](https://helpcenter.onlyoffice.com/docs/installation/docs-community-sys-reqs-docker.aspx)); Collabora is MPL-2.0 with a 490 MB image ([Docker Hub](https://hub.docker.com/v2/repositories/collabora/code/tags?page_size=6&ordering=last_updated)), but its free CODE build is "not suitable for production" ([Collabora](https://www.collaboraonline.com/blog/understanding-the-differences-between-code-and-collabora-online/)); the Euro-Office fork is in a public licence dispute with ONLYOFFICE ([The Register](https://www.theregister.com/2026/04/02/eurooffice_forks_onlyoffice/)); Microsoft's WOPI route is restricted to cloud-storage vendors ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/online/overview)). Under the FSF's view, a separate unmodified server reached over sockets is normally a separate program ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html)), so an optional, user-installed sidecar is defensible; a Docker dependency is still wrong for a default laptop install.

| Where it can live | Components | Condition |
|---|---|---|
| Inside the Apache-2.0 repo | IronCalc, Fortune-sheet, ExcelJS, SheetJS CE (from its CDN), docx.js, mammoth, ProseMirror, Tiptap core, BlockNote core (MPL: keep changes public), eigenpal core, PptxGenJS, pptx-automizer, dom-to-pptx, OfficeCLI, LibreOffice and its kit (MPL-2.0, unmodified), pdf.js, pdfmake, pypdf, Tesseract | Vendor with NOTICE entries and sha256, as the repo already does |
| Private paid repo only | Univer Pro, SpreadJS, eigenpal Pro, Tiptap Pro, BlockNote xl packages, SuperDoc commercial, SheetJS Pro, HyperFormula commercial | Each vendor must also allow redistribution to end users |
| Separate user-installed program, or avoid | ONLYOFFICE, Collabora, pandoc (GPL), Poppler (GPL), PPTist, SuperDoc free tier, MuPDF, Ghostscript (AGPL), Handsontable | Never bundled or linked; legal review first |

## Kybernos ships panels and previews but no way to create, list or edit Office files

The audit read `dev` (HEAD `b0b28d69`), not the assigned worktree, which sits on release 0.1.1, 1,256 commits behind (repo audit). Kybernos ships **no Office or PDF tooling**: the skills it seeds are five, none of them Office ([`index.js`](packages/kybernos-plugin/index.js)). Its "Featured" list and onboarding packs instead point at the four Anthropic skills, fetched from GitHub at install time ([featured-picks.json](packages/kybernos-skills/featured-picks.json)). Those skills assume openpyxl, pandas, npm `docx`, LibreOffice and Poppler, and on the reference Mac none is present: Python 3.9.6 imports none of the libraries, there is no `soffice`, `pdftoppm` or `qpdf`, and only pandoc, uv, npx and the owner's personal `officecli` exist. The repo says as much: its own prompts use "live formulas and a cross-check instead of a LibreOffice recalculation, which this machine does not have" ([templates catalogue](docs/dev/templates-catalogue.md)). The only Kybernos-written readers are small pure-Node, read-only parsers for xlsx into Tables and for docx and PDF text. The skill licence matters here: by my reading, copying them into a DSH profile is what the Anthropic terms exclude, and the product recommends that act.

The engine itself is stronger than Kybernos's use of it. DSH 0.2.2-alpha.2 includes `dsh-skill-office` with six office skills, but the mount table enables it for the SDK app and shows no row for the web app; the web app instead mounts `dsh-office-to-pdf` and a document-preview sidebar ([engine README](file://~/.dsh/kybernos/moteur/0.2.2-alpha.2/node_modules/@deepseek-ai/dsh-skill-office/README.md)). The native LibreOffice kit (148 MB) is already on the reference disk, and these packages are first-party `@deepseek-ai` ones, so this is the same DSH. The sidebar previews xlsx read-only through FortuneSheet, ExcelJS and SheetJS CE with charts and images stripped, PDFs through pdf.js, and docx and pptx by converting to PDF through LibreOffice. Its own words: "Preview, not editing." ([preview README](file://~/.dsh/kybernos/moteur/0.2.2-alpha.2/node_modules/@deepseek-ai/dsh-client-ui-sidebar-documentpreview/README.md)). The seam for a richer viewer exists without any engine patch: `documentPreviews.register({ priority: 'extension' })`, already used once by the media player. It has no save, dirty or undo contract, and the browser-side workspace API is read-only, so any write-back is a new Kybernos route under the write guard.

Kybernos's own panels are narrower than the shelf's promises. `kybernos-slides` has six layouts and text-only fields, keeps decks in memory (they vanish on restart), has no image, chart or table element, and has no export of any kind ([`index.js`](packages/kybernos-slides/index.js)); its one strength is the round trip where the person retypes text or draws and the agent reads the edits back. Dashboards and Tables are agent-written and human-viewed, and the Tables page states that nothing is edited by hand ([kybernos-db README](packages/kybernos-db/README.md)). The Creations page lists only a fixed set of extensions that omits **docx, xlsx and pptx**, so a file the agent writes in those formats does not appear there ([`index.js`](packages/kybernos-plugin/index.js)). The shelf cards ask for what the stack cannot yet deliver: six doc cards request a .docx, six sheet cards a workbook with live formulas and charts, and nine slides cards ask for charts, columns, timelines and photo strips that the text-only slide model cannot draw.

The constraints are the repo's own rules. Zero new engine patches, never stop DSH from starting, no media or fonts in git, and a 4 MiB limit on every tracked file ([AGENTS.md](AGENTS.md), [garde-depot.mjs](scripts/garde-depot.mjs)). The core client is already at 3,739,209 of 4,194,304 bytes, so a heavy editor cannot go inside it. Two precedents show how to ship megabytes: inline (Mermaid, 3 MB) and a lazily served, guarded host route with pinned hashes (MapLibre, 1 MB). The host supplies React 18; HTML creations run in `sandbox="allow-scripts"` iframes with no bridge to the host (no `postMessage` handler in the core). The real page's content-security policy was never measured. A new plugin needs a manifest, a write-guard test, a live GUI check and a zero-red test gate, and the engine compatibility range is pinned.

The practical reading is that rendering is not the missing capability. What is missing, in the order a person meets it, is a guaranteed runtime to create files, listing in Creations, a way to hand edits back, and a loop that tells the agent what the person meant.

## A three-stage plan, the risks, and the decisions that are the owner's

**Stage 0 (days).** Make agent-made xlsx, docx and pptx visible in Creations (extend the extension list or register a Creations source), add an "open in default app" action, and confirm that the engine preview reloads when the agent rewrites a file, which the engine documents but nobody exercised. Run two 30-minute checks: can the agent in `dsh web` call the LibreOffice kit or `officecli`, and what does Univer's open Slides example actually edit. Write four questions to DreamNum: may Pro packages be redistributed in an Apache-2.0 app installed on end-user machines; what are the terms with no fixed domain; what happens at licence expiry offline; may the plugin's bundled credential be reused.

**Stage 1 (about three weeks, medium).** Build the file layer as Apache-2.0 skills, each the manual of a tested script (the repo's own rule), written clean-room: derive every gotcha with your own tests rather than copying Anthropic's scripts. Base it on OfficeCLI as an optional on-demand download (pinned version, auto-update off, wrapped behind a thin interface so it is swappable), the DSH LibreOffice kit as a separate process for recalculation, conversion and rendering, and Node libraries (docx.js, PptxGenJS) where Node suffices. The loop is validate, render, look, with a cap of three iterations as OpenAI uses for spreadsheets, and a golden corpus of the owner's real workbooks, documents and decks (with charts) diffed after every edit cycle. Retire the Featured pointers to the proprietary skills in the same change.

**Stage 2 (weeks three to ten, medium to large).** First generalise the Annotate loop: select a cell, paragraph or slide region, comment, and the comment reaches the agent. It works on read-only previews, matches what OpenAI and Manus ship, and extends what the slides panel already does. Then slides: widen the scene model, persist, export PPTX natively from the model and PDF from print, and run an overflow and overlap check before export. Then two time-boxed bake-offs (two to three weeks each) for sheets and docs, with the same pass criteria: opens the owner's real files without loss, saves back through a guarded route, loads lazily from files under 4 MiB, cannot stop DSH from starting, and works in the real GUI. For any editor, prefer a sandboxed iframe with a small postMessage bridge, the Manus pattern, which fences React version skew and global CSS and must be built because today's iframes have none. PDF gets pdf.js annotation and HTML-to-PDF, nothing more.

**Stage 3 (owner-gated).** Paid engines enter only as optional private-repo modules behind an adapter interface: SpreadJS, Univer Pro after written terms, or eigenpal Pro, and only if the bake-offs show the open path fails. `dsh-univer-office` can be documented as an optional neighbour once coexistence is tested.

The main risks are these. The runtime gap is real: the kit is a 0.2.x preview, OfficeCLI is young and single-maintainer, and its fidelity claims are self-reported, so every dependency sits behind a wrapper and the golden corpus. LibreOffice fidelity and font substitution will mislead visual checks, and fonts cannot be committed. ExcelJS, pdf-lib and python-pptx are unmaintained, which is another reason for wrappers. Files are an injection channel (hidden text in cells, comments and headers can steer an agent, per Anthropic's own add-in warning, [Word add-in](https://claude.com/docs/office-agents/word.md)), the pdf.js advisory needs its patched version confirmed, and any save route inherits the rule that plugin routes are served before DSH's own login. Scope creep is the largest risk: an editor is a product, not a feature. Engine upgrades can break the preview registry, which is why the compatibility gate exists.

| Decision | Recommended default | Why it is yours |
|---|---|---|
| Do people edit inside Kybernos, or direct the agent and view? | Levels 1 and 2 everywhere, level 3 for slides; decide docs and sheets after the bake-offs | Kybernos's own Tables page already says nothing is edited by hand; a full editor changes the product, not just the code |
| Budget for paid engines | None until a bake-off fails | Prices are quote-only for several engines, and each vendor must also permit redistribution |
| Ask DreamNum for written terms; recommend `dsh-univer-office` or not | Ask, and treat it as an optional neighbour | It is a commercial relationship with a company that also competes |
| Proprietary Anthropic skills | Stop recommending them; ship own Apache-2.0 skills | A licence-risk call (reading, not advice) that needs a lawyer's look |
| On-demand downloads of OfficeCLI (34 MB) or the LibreOffice kit (about 150 MB) | Allow, optional, disclosed | Disk, network and the "never block DSH" rule are product trade-offs |
| PPTX promise | Export from the structured model only | Sets what users may expect from exported decks |

## Conclusion

The decision is less "which editor" than "how far does human editing go", and Kybernos had already answered part of that: its Tables page forbids hand edits, and its slides panel allows only text and drawing. Both fit levels 1 to 3. The cheapest high-value feature turned out to be the one the leaders share and Univer does not sell, a comment channel from the person to the agent, because it makes a read-only preview into a collaboration surface for all four formats without an editor licence. The second novel point is that Manus's real lesson is architectural, not a library list: one isolated engine per format behind a message bridge, which is exactly the shape that Kybernos's "never stop DSH from starting" and 4 MiB rules reward. Third, Univer's strongest asset, its agent harness, is what its vendor now offers DSH users directly, so building on Univer would mean competing with the supplier. Revisit that only when written OEM terms exist, the open Slides UI proves usable, and a bake-off shows the permissive path cannot meet the owner's real files.
